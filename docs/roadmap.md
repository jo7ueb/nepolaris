# 実装ロードマップ（ドラフト）

更新日：2026-11-24

各段階は**会計の不変条件をテストで守りながら**進める。Issueが実行単位であり、この文書は順序と目的を示す。

## Phase 0 — 開発基盤とアーキテクチャ

**ゴール：** 実装方針、プロジェクト構成、テスト・運用の基盤を揃える。

- 要求・不変条件・未決事項のレビューとADR
- モジュラーモノリスを基本とした技術選定（Docker Compose、バックエンド、DB、UI）
- 開発環境、CI、テスト、フォーマット、最低限の認証・秘密情報管理

**完了条件：** 空のアプリをDockerで起動でき、テストがCIで成功する。

## Phase 1 — 複式簿記の核

**ゴール：** 初期残高から元帳・試算表を信頼して算出できる。

- 勘定科目、会計期間、金融口座マッピング
- 仕訳・明細と借貸一致の制約
- 手動仕訳、訂正履歴、開始残高
- 総勘定元帳、試算表、最小限のB/Sと期間収支

**完了条件：** 不均衡仕訳は拒否され、任意の時点で帳簿残高を再現できる。

## Phase 2 — CSV取込と残高照合

**ゴール：** 日々の銀行取引を継続的に記帳できる。

- CSVフォーマットのマッピング、元ファイル保全、プレビュー
- 重複検出、口座間振替の照合、分類ルール
- 承認して仕訳へ変換、再取込の冪等性
- 実口座残高と帳簿残高の照合

**完了条件：** 同じCSVの再取込や振替両側の取込で二重仕訳を作らない。

## Phase 3 — 月末評価と決算

**ゴール：** FX・証券・iDeCoの全取引を記録せず、財務諸表へ正しく取り込める。

- 評価スナップショット（評価対象範囲、基準日、根拠）
- 仕訳プレビューと評価調整、冪等な再処理、訂正
- 月次締め、再オープン、監査可能な変更
- 入力・仕訳・残高照合の整合性テスト

**完了条件：** 前月50万円・純入金10万円・当月末63万円の口座で調整3万円が一度だけ計上され、訂正も追跡できる。

## Phase 4 — 観測・分析と運用完成

**ゴール：** 月に数回の操作で財務状況を観測できる。

- 純資産推移、収支内訳、資産構成・流動性ビュー
- 仕訳・取込・評価・決算を辿れる最小UI
- 安全なデプロイ、バックアップ・リストア、データエクスポート
- 実データではなく匿名・架空データによるエンドツーエンド検証

**完了条件：** 「CSV→月末評価→決算→ダッシュボード」の一連の流れが成立し、復元可能。

## MVP後

- 予算・実績差異と支出アラート
- 財務健全性KPI、資金繰り予測
- 詳細な投資配分・リスク観測
- 必要な場合のみ外貨・複数会計期間等を拡張

## チケット運用

- GitHub Issueは**明確な成果物と受入基準**のある単位で作る。
- 変更が会計の不変条件に触れるときは、影響範囲とテストを必須とする。
- 設計決定は必要に応じてADRを残す。
- 個別Issueの依存関係はIssue本文で明示する。
- 個人の金融データはIssue、PR、CIログ、テストfixtureに投稿しない。
